# Android Platform Engineering

Scope: the Android platform source lanes a Compose-only or single-language body
cannot reach — the View system and XML layouts, Kotlin/Java interop across a mixed
module, and NDK/CMake/JNI native modules (BS §79.7). This skill does not restate
Gradle configuration synthesis, manifest permission derivation, shrinker rule
generation, component lifecycle, background execution, device APIs, or widget
authoring; those are owned by their own skills and by the supervisor-owned
platform target service (TA §73.18.1).

## Trigger
This skill is requested when the construction contract selects the View system with
XML layouts, a module mixing Kotlin and Java, or a native module built through the
NDK and CMake (BS §79.7). It does not replace a worker role — it supplies the
domain instruction the worker executes inside its scoped asset transaction
(BS §50).

## Required capabilities
- `ANDROID_BUILD_TOOLCHAIN`
- `ANDROID_SOURCE_ENGINEERING`

## Preconditions
- The current EnvironmentCapabilityRecord is available and is not stale;
  capability is read from the record, never assumed.
- Every capability listed above resolves to AVAILABLE. When any
  resolves to UNAVAILABLE or USER_REQUIRED, the gated steps MUST NOT
  execute and the blocked state MUST be reported.
- The source revision and, where one exists, the artifact digest are
  known, so every record this skill emits can be bound to them.
- The technology plan already names the lanes in scope. A lane this skill was
  not asked for is not entered speculatively, and a lane the plan names but the
  module does not contain is reported as absent rather than fabricated.

- Gated by the Android toolchain authority (TA §49), independent of the
  host toolchain capability. When `ANDROID_BUILD_TOOLCHAIN` or
  `ANDROID_SOURCE_ENGINEERING` resolves to UNAVAILABLE or USER_REQUIRED, the
  gated steps MUST NOT execute and the blocked state MUST be reported.

## Context requirements
- The task this skill was invoked for, and the outcome the caller expects.
- Revision, and artifact digest where an artifact exists, plus the
  environment fingerprint of the session.
- The module layout, the language split per module, and the declared minimum and
  target API levels, so a lane decision is made against the real module shape.
- The evidence identifiers this run must bind to, so results attach to
  the same evidence graph as the work that preceded them.

## Allowed tools
- view_binding_codegen
- interop_boundary_analysis
- native_module_build
- abi_inspection

## Procedure
1. Read the module's language and layout shape first: which modules are Kotlin,
   which are Java, which declare XML layouts, and which declare a native build.
   Record the observation instead of assuming a uniform project.
2. View lane — enable ViewBinding for the modules that declare XML layouts and
   bind through the generated class. Never hand-written findViewById chains and
   never a mix of both in one module; the two coexist only across a module
   boundary with a stated reason.
3. View lane — resolve view state through the lifecycle owner the module already
   uses, keep the bound reference valid only for the view's own lifetime, and
   release it in the matching teardown. A binding that outlives its view is a
   leak, not a cache.
4. View lane — for a recycling list, bind the item layout once per holder, reset
   every recycled field on rebind, and keep the adapter's diffing explicit. A
   field that survives a rebind from the previous item is a correctness defect
   that no build reports.
5. Interop lane — treat the Kotlin/Java boundary as an API surface: mark members
   that Java must see, keep internal declarations out of the exported surface,
   state nullability explicitly where Java cannot infer it, and give every
   cross-language call a single unambiguous overload.
6. Interop lane — align the standard library artifact with the Kotlin version the
   module actually compiles against, and route asynchronous work across the
   boundary through one adapter rather than nesting two concurrency models.
7. Native lane — wire the external native build to the module that owns it, keep
   the native build configuration and the packaged shared library per build
   variant, and confirm the declared ABIs include the ABI the Nirman-managed
   local Android emulator runs.
8. Native lane — keep every JNI entry point's signature exactly matched to its
   exported symbol, including the mangled name a Kotlin member receives, and load
   the library once at a point that runs before first use. Shrinker keep rules
   for these entry points are generated by the platform target service
   (TA §73.18.4); this skill states the signature reality, not the rule.
9. Emit the result bound to the revision, and name each lane separately as
   entered, absent, or unverifiable, so a lane that was not exercised is never
   read as one that was.

## Evidence
- A record of each procedure step that executed, with the outcome observed,
  bound to the source revision and the environment fingerprint.
- The emitted `AndroidPlatformSourceResult` (§23 SkillPackage contract), carrying its
  classification and its evidence references.
- Invariant claims this skill must leave observable, each of which is a
  statement the evidence above has to support:

  * A lane is reported as entered only when the module was observed to contain
    it; a lane named by the plan but absent from the module is reported absent.
  * A build that compiles is not a lane that works. View inflation, a
    cross-language call across the boundary, and a native call into a loaded
    library each need their own observation, and each is reported unverified
    until one exists.
  * Runtime evidence for any lane requires an observation from the
    Nirman-managed local Android emulator bound to the environment fingerprint.
    A missing or unstartable emulator is USER_REQUIRED, never a simulated device.
  * A native lane whose declared ABIs exclude the emulator's ABI is reported as
    unrunnable, never as passed; an ABI mismatch is a build-configuration fact,
    not a flaky result.
  * Gradle configuration, permission derivation, shrinker rules, and target API
    deadlines are owned by the platform target service (TA §73.18.1). This skill
    consumes their output and never restates or overrides it.
  * A language boundary is verified at the call site, not inferred from a
    successful compile of the file that declares it.
  * Nothing unverified is reported as verified; an unverified outcome is
    reported as unverified.

## Failure classification
- BLOCKED — a required capability resolves to UNAVAILABLE or USER_REQUIRED;
  the gated steps MUST NOT execute and the blocked state MUST be reported.
- PRECONDITION_UNMET — a precondition below was not satisfied; the skill
  does not proceed past it.
- ACTION_FAILED — a procedure step was attempted and did not produce its
  expected outcome.
- INVARIANT_VIOLATED — the work completed but one of the invariant claims
  this skill must leave observable does not hold.
- TIMEOUT — a wait exceeded its bound; an unbounded wait is a hang, not a
  slow step.

- VIEW_BINDING_ABSENT — a module declaring XML layouts resolves views without generated binding.
- RECYCLED_STATE_LEAK — a recycled item view carries a field from the previously bound item.
- INTEROP_SIGNATURE_AMBIGUOUS — a cross-language declaration resolves to more than one overload, or a member Java must see is not exposed.
- NATIVE_SYMBOL_MISMATCH — a JNI entry point's signature does not match the exported symbol it claims to reach.
- NATIVE_ABI_UNSUPPORTED — the declared ABIs exclude the ABI required to run the module where it must be observed.

## Recovery
- A blocked capability resumes when the capability record changes; the blocked
  node names its resume condition and is never reported as a failure of the
  goal.
- One retry is permitted after a repair that materially changed the input. An
  identical action is never re-run against unchanged evidence, and the
  recoveryAttemptPolicy bound escalates rather than terminating the goal.
- An invariant violation is repaired at its cause, never by relaxing the check
  that detected it, and never by deleting the lane that failed.
- A lane that cannot be entered on this host is reported as USER_REQUIRED with
  the lane named, so a later session can resume it; it is not dropped silently
  and not converted into a pass.

## Output contract
Emits `AndroidPlatformSourceResult` from `AndroidPlatformSourceRequest` (§23 SkillPackage contract):

- classification: one of the failure classes above, null on success
- laneStates: per lane, entered, absent, or unverifiable
- evidenceRefs: identifiers of the evidence this run captured
- revision and, where one exists, artifactDigest: what the evidence is bound to
- unverified: outcomes this run could not verify, named rather than assumed

## Fixtures
- Step 1 produces its expected outcome — Read the module's language and layout shape first: which modules are Kotlin, which are Java, which declare XML layouts, and which declare a native build.
- Step 2 produces its expected outcome — View lane — bind XML layouts through the generated ViewBinding class, never a hand-written findViewById chain in the same module.
- Step 3 produces its expected outcome — View lane — hold the bound view reference only for the view's own lifetime and release it in the matching teardown.
- Step 4 produces its expected outcome — View lane — reset every field on recycle so no value survives from the previously bound item.
- Step 5 produces its expected outcome — Interop lane — expose exactly one unambiguous cross-language overload per call, with nullability stated where Java cannot infer it.
- Step 6 produces its expected outcome — Interop lane — align the standard library artifact with the Kotlin version the module compiles against and bridge asynchronous work through one adapter.
- Step 7 produces its expected outcome — Native lane — declare ABIs that include the ABI the Nirman-managed local Android emulator runs, and package the native library per build variant.
- Step 8 produces its expected outcome — Native lane — match every JNI signature to its exported symbol, including the mangled name, and load the library before first use.
- Step 9 produces its expected outcome — Emit each lane separately as entered, absent, or unverifiable.
- A module declares no XML layouts, no mixed language, and no native build — every lane reported absent, nothing fabricated
- A required capability is UNAVAILABLE — blocked, nothing attempted
- A native module's declared ABIs exclude the emulator's ABI — reported unrunnable, never passed
- An invariant of this skill is violated and is reported, not absorbed

This skill is permission-neutral (CLAUSE.SKILL.NO_PERMISSION_GRANT); every
execution still passes through ToolBroker and PolicyAuthority.
